# Панель владельца: подготовка Supabase

Код панели подготовлен только для `GRANAT_site_test`. Эта инструкция сама ничего
не выполняет. Политики и настройки меняет владелец вручную после согласования.
Публикация панели — отдельный шаг. Новый пользователь и новые таблицы не нужны.

## Важно перед проверкой

- Тестовый сайт подключён к настоящей таблице `public.products` проекта GRANAT-shop.
  Сохранение в панели изменяет именно её, а не отдельную копию базы.
- Сначала экспортируйте существующие пять строк products в CSV через Table Editor.
- Для проверки добавьте отдельный товар с названием «ТЕСТ — …», сначала скрытый.
  Не меняйте цены пяти утверждённых товаров во время испытаний.
- Не присылайте пароль, access/refresh token или секретные ключи в чат.
- Используется только существующий публичный ключ из `js/supabase-config.js`.
- UUID владельца: `b0aa7109-bc50-4fd4-8ac2-68d4ce73eb7a`.

## 1. Проверить существующую учётную запись

В Authentication → Users откройте своего пользователя и сверьте UUID выше.
Для входа нужен пароль этой учётной записи. Если пароль неизвестен, используйте
средства восстановления Supabase; не создавайте вместо неё нового пользователя.
Публичную регистрацию лучше отключить в настройках Auth. Даже если она включена,
четыре ранее согласованные политики не должны давать чужому пользователю запись.

## 2. Чтение скрытых товаров — настроено владельцем

Владелец подтвердил создание `owner_read_all_products`. Повторно выполнять SQL
не нужно. Ниже сохранены согласованные условия для проверки:

```sql
BEGIN;
CREATE POLICY owner_read_all_products
ON public.products
FOR SELECT
TO authenticated
USING (auth.uid() = 'b0aa7109-bc50-4fd4-8ac2-68d4ce73eb7a'::uuid);
COMMIT;
```

Этот скрипт добавляет отдельную SELECT-политику. Четыре существующие политики
SELECT/INSERT/UPDATE/DELETE оставьте без изменения. Не заменяйте условие владельца
на `true` или просто `auth.role() = 'authenticated'`.
Если такая политика уже есть, не запускайте CREATE повторно: сначала сравните
её условия. Supabase применяет разрешающие политики совместно, поэтому наличие
других широких политик тоже надо проверить.

## 3. Хранилище фотографий — настроено владельцем

Владелец подтвердил существующий bucket `product-images`: публичный, лимит 5 MB.
Повторно создавать bucket или политику не нужно. Параметры для проверки:

1. Имя и ID: `product-images`.
2. Public bucket: включено. Фотографии будут доступны посетителям по прямой ссылке.
3. Ограничение размера: 5 MB (не больше 5 242 880 байт).
4. Разрешённые MIME-типы: `image/jpeg`, `image/png`, `image/webp`.

Публичность даёт чтение фотографий, а не разрешение загружать или удалять их.
Не используйте этот bucket для документов или персональных данных.

Владелец подтвердил политику `owner_upload_product_images`. Ниже её условия
для сверки, не инструкция повторного выполнения:

```sql
BEGIN;
CREATE POLICY owner_upload_product_images
ON storage.objects
FOR INSERT
TO authenticated
WITH CHECK (
  bucket_id = 'product-images'
  AND auth.uid() = 'b0aa7109-bc50-4fd4-8ac2-68d4ce73eb7a'::uuid
);
COMMIT;
```

Панель загружает каждую фотографию с новым случайным именем в папку UUID владельца.
Перезаписи и удаления файлов нет, поэтому UPDATE/DELETE-политики Storage панели
не требуются. Проверьте, что другие политики не открывают запись всем пользователям.
Фотографии из папки images в GitHub не перемещаются и не удаляются.

## 4. Как проверить после отдельного разрешения на публикацию

Адрес панели после публикации тестовой версии:
`https://kurkul1959-hub.github.io/GRANAT_site_test/admin.html`.
До публикации новых файлов этот адрес не является подтверждённо работающим.

1. Без входа панель показывает только форму входа.
2. Существующий владелец входит; видит доступные и скрытые товары.
3. Добавляет скрытый тестовый товар с JPG/PNG/WebP-фотографией.
4. Возвращает его на витрину: после обновления он появляется в ассортименте и доставке.
5. Кнопка «Заказать» добавляет его в тестовую корзину; сумма совпадает с ценой базы.
6. Меняет цену только тестового товара: перед подтверждением заказа корзина просит
   проверить новую сумму. Форма остаётся демонстрационной, реальной отправки нет.
7. Скрывает тестовый товар: он исчезает из витрины и исключается из заказа при
   повторной загрузке/проверке. В панели его по-прежнему видно, можно вернуть.
8. Выходит. Перезагрузка не восстанавливает вышедшую сессию.

Проверка запрета записи для посетителя и постороннего пользователя обязательна
на реальных политиках. Нельзя считать локальные тестовые ответы API доказательством
настройки Supabase. Второго пользователя без отдельного согласования не создаём.

## Ограничения первой версии

- Цены — целые рубли; единица продажи — кг, как в текущем загрузчике сайта.
- Фотографии до 5 MB, без автоматического сжатия; HEIC нужно выбирать/экспортировать
  как JPG. Много крупных фотографий расходуют квоты Storage и исходящего трафика.
- Старые загруженные фото сохраняются. При сбое после загрузки, но до записи товара,
  в Storage может остаться неиспользуемый файл. Удалять его следует отдельно после
  проверки ссылок, а не автоматически при сетевой ошибке.
- Пароль не сохраняется. Auth-сессия хранится в sessionStorage тестовой панели,
  живёт в пределах вкладки и содержит access/refresh token. Вход проверяется через
  Supabase Auth; права на базу обеспечивает RLS. Публичный UUID владельца не секрет.
- Страница admin.html доступна по адресу, но чтение/изменение базы ограничено Auth/RLS.
  `noindex` и отсутствие ссылки в меню не являются защитой.
- При неопределённом сетевом результате записи нужно обновить список перед повтором,
  особенно при добавлении товара, чтобы не создать дубликат.
- Одновременное редактирование с двух устройств: последний сохранённый вариант
  выигрывает. Версионирование/журнал изменений пока не реализованы.
